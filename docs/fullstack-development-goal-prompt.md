# 全栈开发 Goal 模式提示词

请在当前仓库中直接完成个人图片 / 视频作品集网站的全栈开发，不要只输出方案或伪代码。

## 唯一目标

基于以下两类产品资料，交付一个可以本地运行、可测试、可部署到 Vercel 的作品集网站：

1. 产品需求文档：`docs/personal-portfolio-site-prd.md`
2. 页面视觉参考：`docs/previews/README.md` 及其引用的 16 张 PNG 预览图

公开站点要让访客浏览图片和视频作品、了解创作者并提交联系；后台要让站主登录、上传媒体、编辑项目、排序、设置封面、预览、发布、下线和处理联系线索。

## 已确认技术选型（必须遵守）

- 前端：React + TypeScript + Tailwind CSS
- 后端：Node.js
- 部署：Vercel
- 数据库与平台服务：Supabase PostgreSQL；优先使用 Supabase Auth 和 Supabase Storage
- 代码仓库：GitHub

若仓库为空，可使用 Vite + React + TypeScript + Tailwind CSS 建立前端脚手架；后端使用适合 Vercel 的 Node.js Functions/API 路由。若仓库已有脚手架，先理解并复用已有结构，不要无理由重写。

## 开始前必须完成

1. 读取并理解 PRD 全文、页面预览索引和相关 PNG；不要根据页面截图臆测功能，功能以 PRD 为准，截图用于布局、层级、色彩和内容密度参考。
2. 检查仓库已有代码、依赖、环境变量、脚本、数据库迁移、README 和开发约定。
3. 给出一份简短执行计划，明确将修改的文件/模块、已知风险和验证方式，然后立即开始实现。
4. 如果发现真正影响产品方向的问题才提问；技术细节、文件组织和常规实现选择自行决定并继续推进。

## 实现顺序

### 1. 工程基础

- 建立 React + TypeScript + Tailwind CSS 的可运行应用和统一设计令牌。
- 建立 Node.js API 层、错误格式、鉴权中间件、输入校验和日志边界。
- 添加 `.env.example`，只写变量名和用途，不写真实密钥。
- 配置 GitHub 友好的 scripts、lockfile、README 和基础 CI 检查。

### 2. Supabase 数据和安全

- 按 PRD 数据模型建立版本化迁移：`users`、`sessions`、`projects`、`project_assets`、`assets`、`tags`、`project_tags`、`site_settings`、`inquiries`、`upload_tasks`、`audit_logs` 等实际需要的表。
- 使用 Supabase Auth 管理站主登录和会话；不要自行在前端保存密码或伪造登录状态。
- 暴露 schema 中每张业务表启用 RLS；策略按 `owner_id`/站点归属限制读写，公开读取只允许已发布项目。
- UPDATE 策略同时包含 `USING` 和 `WITH CHECK`；不要使用用户可编辑的 `user_metadata` 作为授权依据。
- React 客户端只使用 Supabase publishable/anon key；`service_role`/secret key 只能在 Node.js 服务端环境变量中使用。
- 原始媒体和草稿资产默认私有；用受控 Storage 策略和服务端签发的短时上传/读取凭证访问。
- 如果使用 Storage upsert，补齐 INSERT、SELECT、UPDATE 权限并写替换场景测试。
- 不要把真实密钥、生产数据或媒体文件提交到 GitHub。

### 3. 公开站点

实现并打通以下路由和状态：

- `/` 首页：Hero、精选项目、能力摘要、关于摘要、联系 CTA
- `/work` 作品列表：分类/标签筛选、排序、空状态、URL 可复现筛选
- `/work/:slug` 项目详情：混合图片/视频画廊、海报帧、全屏查看、键盘与触控切换、上下项目导航
- `/about` 关于
- `/services` 服务
- `/contact` 联系表单、隐私同意、成功/失败/重试状态
- `/privacy` 隐私说明
- 404 页面

页面视觉要参考 `docs/previews/01-home.png` 到 `08-404.png`：编辑型画廊、暖白背景、炭黑文字、橄榄色强调、细线网格和充足留白。图片预览中的品牌名、项目名和示例照片都是占位内容，使用可替换的本地示例或真实数据库内容。

### 4. 登录和后台

实现以下后台路由和状态：

- `/admin/login`：邮箱密码登录、错误提示、退出、找回密码入口（邮件服务未配置时明确禁用）
- `/admin`：项目数、草稿数、处理中媒体、未读线索和异常任务
- `/admin/projects`：搜索、状态筛选、精选、排序、软删除/恢复
- `/admin/projects/new` 与 `/admin/projects/:id`：项目字段、Slug、分类、标签、媒体排序、封面、Alt 文本、保存草稿、预览、发布、下线
- `/admin/assets`：媒体库、图片/视频/处理中筛选、上传、进度、失败重试、详情和替换
- `/admin/inquiries`：线索列表、未读/已读/归档、备注、邮件回复入口
- `/admin/settings`：品牌、首页、导航、SEO、社交链接和联系邮箱
- `/admin/account`：个人资料、改密码、会话、二次验证预留、危险操作

页面视觉要参考 `docs/previews/09-admin-login.png` 到 `16-admin-account.png`：深色侧栏、浅色内容区、白色面板和橄榄色主操作按钮。后台所有草稿、线索和媒体 API 都必须经过服务端鉴权与账号归属校验。

### 5. 图片/视频上传闭环

- 前端和服务端都校验扩展名、MIME、文件签名和大小。
- 采用分片/可恢复上传或等价机制，显示每个文件的上传、处理中、可用、失败、取消状态。
- 通过 Supabase Storage 保存对象；服务端生成受控上传凭证，不能把私有存储路径直接暴露给未授权访客。
- 为图片生成缩略图和响应式展示尺寸，为视频生成海报帧、时长和网页播放版本。
- 如果当前环境没有可用的转码服务，先实现可替换的媒体处理适配层和明确的 pending/failed 状态；不要把未完成的转码伪装成已完成。
- 项目发布前必须阻止缺少标题、唯一 Slug、分类、封面、可用资产或 Alt 文本的项目。
- 发布采用原子切换；新媒体处理失败时，已发布项目继续使用旧版本。

## 视觉实现要求

- 优先还原参考图的布局节奏、字体层级、留白、媒体比例、边框和按钮状态，不要用通用 SaaS 模板替代。
- 首屏优先展示作品，避免把长文案和管理字段堆在公开首页。
- 实现响应式桌面/移动布局；图片使用响应式尺寸、懒加载和明确宽高，视频默认静音并提供海报和可见控件。
- 支持 `prefers-reduced-motion`、键盘导航、可见焦点、Esc 关闭画廊、Alt 文本和 WCAG 2.2 AA 基础要求。
- 预览图中的文字可以替换，但必须保留页面语义、层级和交互状态。

## 必须验证的验收标准

### 功能

- 访客可以从首页进入作品详情、浏览图片/视频并提交联系表单。
- 站主可以登录、创建草稿、上传至少一张图片和一个视频、排序、设封面、补 Alt 文本、预览并发布项目。
- 发布项目可在公开 URL 访问；下线后不出现在列表和站点地图。
- 上传中断后可重试/续传；处理失败有错误提示和重试入口。
- 退出后后台 URL 和草稿/私有媒体不可访问；跨账号请求返回 401/403。

### 工程与安全

- `npm`/包管理器 lockfile 已提交，依赖版本明确。
- TypeScript 类型检查、Lint、自动化测试和生产构建通过。
- Supabase 迁移、RLS、Storage 策略可复现；没有把 `service_role`/secret key 暴露到客户端。
- `.env.example` 完整，README 写明本地启动、Supabase 初始化、迁移、测试和 Vercel 部署步骤。
- GitHub PR 可触发 Vercel Preview；Preview 和 Production 使用分离环境变量。

### 性能与可访问性

- 首页移动端首屏目标 LCP p75 ≤ 2.5 秒；首屏图片/视频不会一次性加载全部原始媒体。
- 自动化可访问性扫描没有严重级别问题；键盘可以完成导航、打开/关闭画廊和提交表单。

## 工作方式与汇报

- 持续推进，不因普通实现困难停在分析阶段。
- 每个阶段汇报：已完成修改、文件/模块位置、测试和验证证据、未完成事项、下一步动作。
- 区分静态检查、自动化测试、本地运行测试和真实人工验收；没有执行的验证不要声称完成。
- 保留 PRD 中已有功能、数据结构、账号隔离、背景 ID、二三级卡片联动和 API 语义；如需兼容调整，先记录影响并采用兼容方案。
- 完成前不要只给截图或静态页面；必须让核心公开浏览、登录、后台 CRUD、上传和发布链路在本地可运行。
